Full Setup

Installation and License

Everything you need to get the resource up and running. The license (key) is part of the installation, so it's all together here.

1. Extract the resource

Place the MathStoreFairyWing-V7 folder inside your resources/ folder.

Folder nameThe folder name must be exactly MathStoreFairyWing-V7. Keybinds, internal events and state bags depend on this name.

2. Configure the Key (Convar)

Each server needs a unique key for the resource to work. This key is configured as a convar in your server.cfg, and must come before the ensure.

server.cfg
## ─── MathStore Fairy Wing V7 ───

# 1. Set the key (BEFORE the ensure)
set mathstore_key_fairyv7 "AP-XXXX-XXXX-XXXX"

# 2. Start the resource
ensure MathStoreFairyWing-V7
Protect your keyDo not share your key. Each key is bound to the server IP. If you change hosts, contact us to migrate.

Configuration

Config.lua

The config/config.lua file centralizes all resource options. Everything you can change is here.

Framework and General

config.lua
-- Automatic framework detection
Config.Framework = 'auto'     -- 'auto' | 'qbx' | 'qb' | 'esx' | 'vrp' | 'standalone'

-- Use ox_lib for commands and notifications
Config.UseOxLib = true

-- System language (notifications, keybinds, HUD)
Config.Locale = 'pt-BR'      -- 'pt-BR' | 'en-US' | 'es' | 'fr' | 'pt-PT' | 'th'
TipWith Config.Framework = 'auto', the resource detects which framework is running on its own. Only force it manually if you have a conflict.

Notifications

config.lua
Config.Notifications = {
    type     = 'auto',    -- 'auto' | 'ox_lib' | 'qb' | 'esx' | 'vrp' | 'native'
    duration = 5000,     -- Duration in milliseconds
}

Multi-Framework

Bridge System

The resource automatically detects the server's framework and adapts all internal functions. You don't need to configure anything in most cases.

How detection works

In bridge/shared.lua, the system checks which resources are running and picks the correct bridge:

QBX (Qbox)qbx_core'qbx'

Bridge Functions (Server-side)

Functions available on the server to interact with player data:

server
-- Get the player object from the framework
local player = Bridge.GetPlayer(source)

-- Get unique identifier (citizenid, identifier, user_id)
local cid = Bridge.GetCitizenId(source)

-- Character name from the framework
local name = Bridge.GetPlayerName(source)

-- Current job (name + grade)
local job = Bridge.GetJob(source)

-- Check permission (multi-layer system)
local allowed = Bridge.HasPermission(source, 'use')

-- Send notification (adapts to detected framework)
Bridge.Notify(source, 'Message', 'success')

-- Execute callback defined in config
Bridge.ExecuteCallback('CanEquipWings', source, cor)

Functions available on the client:

client

-- Has the player finished loading?

-- Client-side notification
Bridge.ShowNotification('Text', 'info', 5000)

local has = Bridge.HasOxLib()
Access Control

Permissions System

Controls who can use each resource feature. The system has 8 check layers, verified in order. When any layer gives a definitive response (allow or deny), the remaining layers are skipped.

Permission Keys

There are two keys used throughout the system:

KeyWhere it's usedDescription
'use'All wing commands, HUD, animationsGeneral permission to use the resource
'admin_cleanup'/asaslimpar7Admin permission to clean up all wings on the server

Full check flow (8 layers)

When a player executes any command, permission is checked in this order:

1. Config.Callbacks.HasPermission(source, permission) → Returns true/false? Uses it and stops here → Returns nil? Continues to next layer 2. ACE Permission: IsPlayerAceAllowed(source, Permissions.Ace[perm]) → E.g.: 'fairy.use' 3. Feature Config: Permissions.Features[perm].enabled → If enabled = false, EVERYONE has access (no restriction) 4. CitizenID: Permissions.Features[perm].citizenids → List of specific allowed IDs 5. vRP Groups: Permissions.VRP[perm] → E.g.: {'Fada', 'Admin'} 6. Sets (QBX): Permissions.Features[perm].sets 7. ACE Groups: Permissions.Groups[group] → Checks group.admin, group.vip, etc. 8. Jobs: Permissions.Features[perm].jobs → E.g.: {'police', 'ambulance'}

Allow for everyone (no restrictions)

permissions.lua
Permissions.Features = {
    use = {
        enabled = false,    -- false = EVERYONE can use, no checks
    },
}

Restrict by vRP group

permissions.lua
Permissions.VRP = {
    use = { 'Fada', 'Admin' },            -- Exact vRP group names
    admin_cleanup = { 'Admin' },
}

Restrict by ACE Permission

permissions.lua
Permissions.Ace = {
    use = 'fairy.use',
    admin_cleanup = 'fairy.admin',
}
server.cfg
# Grant usage to VIP group
add_ace group.vip fairy.use allow

# Grant admin cleanup
add_ace group.admin fairy.admin allow

Restrict by Job (QB/ESX)

permissions.lua
Permissions.Features = {
    use = {
        enabled = true,
        jobs = { 'police', 'ambulance' },   -- Job name in the framework
    },
}

Restrict by specific CitizenID

permissions.lua
Permissions.Features = {
    use = {
        enabled = true,
        citizenids = { 'ABC12345', 'XYZ67890' },
    },
}

Callbacks

Callbacks: Injecting Your Server Logic

Callbacks allow you to write your own logic within the resource flow, without editing any internal files. Everything stays in config/config.lua. Use them to decide who can use it, what happens when equipping, what happens when removing, and any custom rule from your server.

Callback Table

CallbackParametersReturnWhen it's called
CanOpenHUDsourcetrue/falseBefore opening the radial HUD
CanEquipWingssource, cortrue/falseBefore equipping wings
OnWingsEquippedsource, cornoneAfter equipping wings
OnWingsRemovedsourcenoneAfter removing wings
HasPermissionsource, permissiontrue/false/nilBefore any permission check
About CanEquipWingsThe cor parameter can be nil or a number. When it's nil, the server is checking whether the "Get Wings" button on the HUD should be enabled. When it's a number, it's an actual equip attempt. Handle both cases in your callback.

Scenarios with complete examples

Each scenario below is complete and self-contained. Copy whatever makes sense for your server.

Require inventory item to equip (and return on remove) ESX

The player needs to have the fairy_essence item in their inventory. On equip, the item is consumed. When the wings are removed, the item is returned to the inventory.

config.lua
Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if cor then
            -- Actual equip attempt: check item
            local xPlayer = ESX.GetPlayerFromId(source)
            local item = xPlayer.getInventoryItem('fairy_essence')
            if not item or item.count < 1 then
                Bridge.Notify(source, 'Fairy Essence required!', 'error')
                return false
            end
            return true
        end
        -- cor = nil: just checking if the HUD shows the button
        return true
    end,

    OnWingsEquipped = function(source, cor)
        -- Remove item from inventory after equipping
        local xPlayer = ESX.GetPlayerFromId(source)
        xPlayer.removeInventoryItem('fairy_essence', 1)
    end,

    OnWingsRemoved = function(source)
        -- Return item on remove
        local xPlayer = ESX.GetPlayerFromId(source)
        xPlayer.addInventoryItem('fairy_essence', 1)
    end,
}
Require inventory item to equip (and return on remove) QB-Core

Same logic as ESX, but using QB-Core functions.

Config.Callbacks = {

        return true

        Player.Functions.RemoveItem('fairy_essence', 1)
    end,

    end,
}
Require inventory item to equip (and return on remove) vRP

Same logic using vRP functions.

config.lua
Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if cor then

            if not user_id then return false end
            local amount = vRP.getInventoryItemAmount(user_id, 'essencia_fada')

        vRP.tryGetInventoryItem(user_id, 'essencia_fada', 1)
    end,

    OnWingsRemoved = function(source)
        local user_id = vRP.getUserId(source)
        vRP.tryGiveInventoryItem(user_id, 'essencia_fada', 1)
    end,
}
Player must be at a specific location Any Framework

The player can only equip wings if they are within a defined area. Useful for creating "temples", altars, or magical zones where wings are unlocked.

config.lua
-- Allowed area (center coordinates + radius)
local ZONA_ALTAR = { x = -1042.5, y = -2745.3, z = 13.9, raio = 15.0 }

Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if cor then
            -- Get the player's current position
            local ped = GetPlayerPed(source)
            local coords = GetEntityCoords(ped)

            -- Calculate distance to the altar
            local dx = coords.x - ZONA_ALTAR.x
            local dy = coords.y - ZONA_ALTAR.y
            local dz = coords.z - ZONA_ALTAR.z
            local dist = math.sqrt(dx*dx + dy*dy + dz*dz)

            if dist > ZONA_ALTAR.raio then
                Bridge.Notify(source, 'You must be at the Fairy Altar!', 'error')
                return false
            end
        end
        return true
    end,
}

Combine multiple rules: item + location + level ESX

Complete example combining multiple conditions. The player needs to have an item, be at a specific location, and have a minimum level. Shows how to compose complex rules in a single callback.

config.lua
local ALTAR = { x = -1042.5, y = -2745.3, z = 13.9, raio = 15.0 }

Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if not cor then return true end  -- HUD check: allow visual

        -- Rule 1: Needs the item
        local xPlayer = ESX.GetPlayerFromId(source)
        local item = xPlayer.getInventoryItem('fairy_essence')
        if not item or item.count < 1 then
            Bridge.Notify(source, 'Fairy Essence required!', 'error')
            return false
        end

        -- Rule 2: Must be at the altar
        local ped = GetPlayerPed(source)
        local c = GetEntityCoords(ped)
        local dist = #(vector3(c.x, c.y, c.z) - vector3(ALTAR.x, ALTAR.y, ALTAR.z))
        if dist > ALTAR.raio then
            Bridge.Notify(source, 'Go to the Fairy Altar!', 'error')
            return false
        end

        -- Rule 3: Minimum level (export from your system)
        local level = exports['meu_level_system']:getLevel(source)
        if level < 30 then
            Bridge.Notify(source, 'You must be level 30!', 'error')
            return false
        end

        return true
    end,

    OnWingsEquipped = function(source, cor)
        local xPlayer = ESX.GetPlayerFromId(source)
        xPlayer.removeInventoryItem('fairy_essence', 1)
        exports['meu_level_system']:addXP(source, 50)
    end,
}
Full permission override with custom logic Any Framework

If you have your own permission system on the server and want to completely bypass the 8-layer system, use the HasPermission callback. Returning true or false skips all default checks. Returning nil lets the system continue normally.

config.lua
Config.Callbacks = {
    HasPermission = function(source, permission)
        if permission == 'use' then
            -- Use your own permission system
            return exports['meu_perm_system']:hasPermission(source, 'fairy_wings')
        end

        if permission == 'admin_cleanup' then
            return IsPlayerAceAllowed(source, 'group.admin')
        end

        return nil  -- For any unknown permission, use default
    end,
}
Permission based on Discord roles Any Framework

Let's say you want to base your permission system on Discord roles. This is possible! Just have a Discord integration resource on the server (like badger_discord_api, discord_perms, deek_discord, etc.) that provides an export to check roles. The HasPermission callback does the rest.

config.lua
Config.Callbacks = {
    HasPermission = function(source, permission)
        if permission == 'use' then
            -- ID of the "Fairy" role on Discord (right-click the role > Copy ID)
            local hasCargo = exports['badger_discord_api']:isRolePresent(source, 1234567890123456)
            return hasCargo  -- true = has role, false = doesn't have it
        end

        if permission == 'admin_cleanup' then
            -- ID of the "Admin" role on Discord
            return exports['badger_discord_api']:isRolePresent(source, 9876543210987654)
        end

        return nil  -- other permissions: use default system
    end,
}
Combining Discord + default systemIf you want the player to have access if they have the Discord role OR if they pass the default system (vRP, ACE, job, etc.), just return nil when the role is not found. This way the system continues checking the other 7 layers normally:
config.lua
Config.Callbacks = {
    HasPermission = function(source, permission)
        if permission == 'use' then
            local discordOk = exports['badger_discord_api']:isRolePresent(source, 1234567890123456)
            if discordOk then return true end
            return nil  -- no Discord role? let the default system check vRP/ACE/etc
        end
        return nil
    end,
}
Events and Integration

Events: Listening and Integrating

The resource fires various events throughout the wing lifecycle. You can listen to these events from other resources to create integrations, synchronize systems, or react when something happens.

Event naming convention

All events are automatically prefixed with the resource name to avoid conflicts. The prefix follows this pattern:

lua
-- Format: ResourceName:type:action
-- Example:
'MathStoreFairyWing-V7:spawn'          -- Command (server → client)
'MathStoreFairyWing-V7:sync:spawned'   -- Synchronization (client → server)
'MathStoreFairyWing-V7:sync:spawn'     -- Broadcast (server → other clients)
About the namesThe exact names are generated automatically in bridge/shared.lua using GetCurrentResourceName(). Below, we use the default name MathStoreFairyWing-V7.

When the player does something locally, the client sends these events to the server so other players can see:

Integration scenarios with complete examples

Each scenario below shows how to listen or react to resource events from another resource on your server.

React when a player starts or stops flying Client - Other Resource

Your HUD resource or status system can listen to flight start/end to show an indicator, apply an effect, or change the camera.

client.lua (other resource)
-- Player started flying
AddEventHandler('flight:start', function(playerId)
    print('[MyHUD] Player flying: ' .. playerId)
    -- Activate flight indicator on the HUD
    SendNUIMessage({ action = 'showFlightIndicator', active = true })
end)

-- Player stopped flying
AddEventHandler('flight:end', function(playerId)
    print('[MyHUD] Player landed: ' .. playerId)
    SendNUIMessage({ action = 'showFlightIndicator', active = false })
end)

-- Flight animation changed (e.g.: gliding, flapping, descending)
AddEventHandler('flight:animationChange', function(playerId, state)
    print('[MyHUD] Flight animation: ' .. state)
end)

Listen on the server when someone equips/removes wings Server - Other Resource

From another server resource, you can listen to sync events to log, give rewards, notify Discord, etc.

server.lua (other resource)
-- Listen when someone equipped wings
RegisterNetEvent('MathStoreFairyWing-V7:sync:spawned')
AddEventHandler('MathStoreFairyWing-V7:sync:spawned', function(cor, initialState)
    local src = source
    print('[Log] Player ' .. src .. ' equipped wings color ' .. cor)

    -- Example: send to Discord
    exports['discord_log']:sendLog('wings', 
        GetPlayerName(src) .. ' equipped wings (color ' .. cor .. ')'
    )
end)

-- Listen when someone removed wings
RegisterNetEvent('MathStoreFairyWing-V7:sync:removed')
AddEventHandler('MathStoreFairyWing-V7:sync:removed', function()
    local src = source
    print('[Log] Player ' .. src .. ' removed wings')
end)
About listening to net eventsWhen you register a RegisterNetEvent from another resource, you are listening to the same event that Fairy Wing V7 already listens to internally. FiveM allows multiple handlers. Your logic runs alongside it, without interfering with the original resource.
React to another player's animation changes Client - Other Resource

When another player changes animation (e.g.: opens wings), the broadcast reaches your client. You can use it to create synchronized visual effects.

client.lua (other resource)
RegisterNetEvent('MathStoreFairyWing-V7:sync:anim')
AddEventHandler('MathStoreFairyWing-V7:sync:anim', function(serverId, animKey)
    print('[Sync] Player ' .. serverId .. ' changed animation to: ' .. animKey)

    -- Example: Create particles around when someone opens wings
    if animKey == 'open' or animKey == 'bater' then
        local ped = GetPlayerPed(GetPlayerFromServerId(serverId))
        if ped and ped ~= 0 then
            -- Add particle to the ped
        end
    end
end)

Triggering Fairy Wing V7 events from another resource

The scenarios above show how to listen to events. But you can also trigger Fairy Wing V7 events directly from your resource, without depending on commands. This is useful when the flow starts outside Fairy Wing V7 (shop, item, NPC, quest, etc.).

ImportantWhen you trigger the event directly, you bypass the Fairy Wing V7 permissions and callbacks system. The responsibility to check whether the player can or cannot use it falls on YOUR resource. Only use this when you want full control of the flow.
Shop or NPC that gives wings to the player on purchase Server - Other Resource

The player interacts with an NPC or shop, pays, and receives wings directly. From your resource's server, you send the :spawn event to the player's client.

server.lua (other resource - e.g.: shop)
-- Player bought wings at the shop, color 5
RegisterNetEvent('minhaLoja:comprarAsas')
AddEventHandler('minhaLoja:comprarAsas', function(cor)
    local src = source

    -- Your payment logic
    local xPlayer = ESX.GetPlayerFromId(src)
    if xPlayer.getMoney() < 5000 then
        TriggerClientEvent('esx:showNotification', src, 'Not enough money!')
        return
    end
    xPlayer.removeMoney(5000)

    -- Give wings to the player (triggers directly on Fairy Wing V7)
    TriggerClientEvent('MathStoreFairyWing-V7:spawn', src, cor)
end)
Usable item that equips wings when used ESX

You register a usable item on the server. When the player uses the item, wings are equipped automatically and the item is consumed.

server.lua (other resource - e.g.: items)
-- Register usable item 'asas_de_fada'
ESX.RegisterUsableItem('asas_de_fada', function(source)
    local src = source
    local xPlayer = ESX.GetPlayerFromId(src)

    -- Consume the item
    xPlayer.removeInventoryItem('asas_de_fada', 1)

    -- Equip wings color 1
    TriggerClientEvent('MathStoreFairyWing-V7:spawn', src, 1)
end)
Usable item that equips wings when used QB-Core

Same logic as ESX, but using QB-Core.

server.lua (other resource - e.g.: items)
-- Register usable item 'asas_de_fada'
QBCore.Functions.CreateUseableItem('asas_de_fada', function(source)
    local src = source
    local Player = QBCore.Functions.GetPlayer(src)

Full flow: from command to synchronization

To understand how everything connects, here is the complete flow when a player types /asas7 5:

Player: /asas7 5 ↓ Server: Receives registered command ↓ Bridge.HasPermission(source, 'use') → 8-layer check (see Permissions section) ↓ NO permission? → Bridge.Notify() + STOP ↓ Bridge.ExecuteCallback('CanEquipWings', source, 5) → Runs the callback from your config.lua ↓ Callback returned false? → STOP ↓ TriggerClientEvent(':spawn', source, 5) ↓ Client: Creates the wing entity, applies color 5 ↓ TriggerServerEvent(':sync:spawned', 5, 'idle') ↓ Server: Saves in activeWings[source] Bridge.ExecuteCallback('OnWingsEquipped', source, 5) ↓ broadcastBucket(':sync:spawn', bucket, source, src, 5, 'idle') ↓ Other players in the same bucket see the wings appear

HUD and NUI

The radial HUD uses FiveM's NUI system. When the player opens the HUD, the client sends data to the embedded browser:

client (internal)

    locale       = HudLocales[...], -- Translated texts (i18n)
})

-- Close HUD

end)

Advanced Topics

Routing Buckets, StateBag and Internal State

Advanced information about how the resource manages synchronization, multi-resource conflicts, and internal state.

Routing Buckets

The resource respects FiveM routing buckets. Players in different buckets don't see each other's wings. All synchronization is filtered by bucket.

server (internal)
-- Each player with wings has their bucket tracked
activeWings[serverId] = {
    cor    = 5,
    state  = 'idle',
    bucket = 0,
}

-- Broadcasts only send to players in the same bucket
broadcastBucket(eventName, bucket, excludeSource, ...)

-- When the bucket changes (checked every 2s):
-- Player changes bucket 0 → bucket 5
--   Players in bucket 0: receive :sync:remove
--   Players in bucket 5: receive :sync:spawn + state
In practiceIf you use apartments, instances, or any system based on routing buckets (e.g.: qb-apartments, esx_property), the wings work correctly in each instance without interfering with the others.

StateBag (Multi-Resource)

If the server has multiple MathStore wing resources (e.g.: DragonWings + DemonWings), the system uses StateBag to avoid conflicts. Only one resource can have active wings per player.

lua
-- Key used in the state bag
WING_STATE_KEY = 'activeWingResource'

-- When equipping wings, the server sets:
Player(src).state:set(WING_STATE_KEY, RES_NAME, true)

-- If another wing resource tries to equip on the same player:
-- Checks if there's already an active resource
-- If there is, can auto-remove the previous one

-- The client listens to changes via:
AddStateBagChangeHandler(WING_STATE_KEY, ...)

Server internal state

The server maintains state tables that track everything that is active. Useful for understanding debug and behavior:

server (internal)
-- 1. Active wings (indexed by server ID)
activeWings[serverId] = {
    cor    = 5,
    state  = 'idle',
    bucket = 0,
}

-- Everything is cleaned up automatically when the player disconnects
