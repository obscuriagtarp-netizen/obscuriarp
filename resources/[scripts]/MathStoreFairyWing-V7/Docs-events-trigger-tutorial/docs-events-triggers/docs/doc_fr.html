Configuration Complete

Installation et Licence

Tout ce dont vous avez besoin pour mettre la resource en ligne. La licence (key) fait partie de l'installation, donc tout est regroupe ici.

1. Extraire la resource

Placez le dossier MathStoreFairyWing-V7 dans votre dossier resources/.

Nom du dossierLe nom du dossier doit etre exactement MathStoreFairyWing-V7. Les keybinds, evenements internes et state bags dependent de ce nom.

2. Configurer la Key (Convar)

Chaque serveur a besoin d'une key unique pour que la resource fonctionne. Cette key est configuree comme une convar dans votre server.cfg, et doit etre placee avant le ensure.

server.cfg
## ─── MathStore Fairy Wing V7 ───

# 1. Definir la key (AVANT le ensure)
set mathstore_key_fairyv7 "AP-XXXX-XXXX-XXXX"

# 2. Demarrer la resource
ensure MathStoreFairyWing-V7
Attention a la keyNe partagez pas votre key. Chaque key est liee a l'IP du serveur. Si vous changez d'hebergeur, contactez-nous pour la migration.

3. Dependances

ResourceStatutFonction

Configuration

Config.lua

Le fichier config/config.lua centralise toutes les options de la resource. Tout ce que vous pouvez modifier se trouve ici.

Framework et General

config.lua
-- Detection automatique du framework
Config.Framework = 'auto'     -- 'auto' | 'qbx' | 'qb' | 'esx' | 'vrp' | 'standalone'

-- Utiliser ox_lib pour les commandes et notifications
Config.UseOxLib = true

-- Langue du systeme (notifications, keybinds, HUD)
Config.Locale = 'pt-BR'      -- 'pt-BR' | 'en-US' | 'es' | 'fr' | 'pt-PT' | 'th'
AstuceAvec Config.Framework = 'auto', la resource detecte automatiquement quel framework est en cours d'execution. Ne forcez manuellement que si vous avez un conflit.

Notifications

config.lua
Config.Notifications = {
    type     = 'auto',    -- 'auto' | 'ox_lib' | 'qb' | 'esx' | 'vrp' | 'native'
    duration = 5000,     -- Duree en millisecondes
}

Multi-Framework

Systeme Bridge

La resource detecte automatiquement le framework du serveur et adapte toutes les fonctions internes. Vous n'avez rien a configurer dans la plupart des cas.

Comment fonctionne la detection

Dans bridge/shared.lua, le systeme verifie quelles resources sont en cours d'execution et choisit le bridge correct :

FrameworkResource DetecteeResultat
QBX (Qbox)qbx_core'qbx'
QB-Coreqb-core'qb'
ESXes_extended'esx'
vRPvrp'vrp'
Aucun-'standalone'

Fonctions du Bridge (Server-side)

Fonctions disponibles cote serveur pour interagir avec les donnees du joueur :

server
-- Obtenir l'objet joueur du framework
local player = Bridge.GetPlayer(source)

-- Obtenir l'identifiant unique (citizenid, identifier, user_id)
local cid = Bridge.GetCitizenId(source)

-- Nom du personnage dans le framework
local name = Bridge.GetPlayerName(source)

-- Job actuel (nom + grade)
local job = Bridge.GetJob(source)

-- Verifier la permission (systeme multi-couches)
local allowed = Bridge.HasPermission(source, 'use')

-- Envoyer une notification (s'adapte au framework detecte)
Bridge.Notify(source, 'Message', 'success')

-- Executer un callback defini dans le config
Bridge.ExecuteCallback('CanEquipWings', source, cor)

Fonctions disponibles cote client :

local has = Bridge.HasOxLib()
Controle d'Acces

Systeme de Permissions

Controle qui peut utiliser chaque fonctionnalite de la resource. Le systeme possede 8 couches de verification, executees dans l'ordre. Lorsqu'une couche donne une reponse definitive (autoriser ou refuser), les suivantes ne sont pas verifiees.

Cles de Permission

Il existe deux cles utilisees dans tout le systeme :

CleOu elle est utiliseeDescription
'use'Toutes les commandes d'ailes, HUD, animationsPermission generale pour utiliser la resource
'admin_cleanup'/asaslimpar7Permission admin pour supprimer toutes les ailes du serveur

Flux complet de verification (8 couches)

Quand un joueur execute une commande, la permission est verifiee dans cet ordre :

1. Config.Callbacks.HasPermission(source, permission) → Retourne true/false ? Utilise et s'arrete ici → Retourne nil ? Continue a la couche suivante 2. ACE Permission: IsPlayerAceAllowed(source, Permissions.Ace[perm]) → Ex: 'MathStoreFairyWing-V7.use' (genere automatiquement) 3. Feature Config: Permissions.Features[perm].enabled → Si enabled = false, TOUS ont acces (sans restriction) 4. CitizenID: Permissions.Features[perm].citizenids → Liste d'IDs specifiques autorises 5. vRP Groups: Permissions.VRP[perm] → Ex: {'Fada', 'Admin'} 6. Sets (QBX): Permissions.Features[perm].sets 7. ACE Groups: Permissions.Groups[groupe] → Verifie group.admin, group.vip, etc. 8. Jobs: Permissions.Features[perm].jobs → Ex: {'police', 'ambulance'}

Autoriser pour tous (sans aucune restriction)

permissions.lua
Permissions.Features = {
    use = {
        enabled = false,    -- false = TOUS peuvent utiliser, sans verification
    },
}

Restreindre par groupe vRP

permissions.lua
Permissions.VRP = {
    use = { 'Fada', 'Admin' },            -- Noms exacts des groupes vRP
    admin_cleanup = { 'Admin' },
}

Restreindre par ACE Permission

La resource genere les noms ACE automatiquement en utilisant GetCurrentResourceName(). Autrement dit, si le dossier est MathStoreFairyWing-V7, les ACEs sont :

permissions.lua
Permissions.Ace = {
    use = GetCurrentResourceName() .. '.use',             -- 'MathStoreFairyWing-V7.use'
    admin_cleanup = GetCurrentResourceName() .. '.admin',  -- 'MathStoreFairyWing-V7.admin'
}
server.cfg
# Autoriser l'utilisation pour le groupe VIP
add_ace group.vip MathStoreFairyWing-V7.use allow

# Autoriser le nettoyage admin
add_ace group.admin MathStoreFairyWing-V7.admin allow

Restreindre par Job (QB/ESX)

permissions.lua
Permissions.Features = {
    use = {
        enabled = true,
        jobs = { 'police', 'ambulance' },   -- Nom du job dans le framework
    },
}

Restreindre par CitizenID specifique

permissions.lua
Permissions.Features = {
    use = {
        enabled = true,
        citizenids = { 'ABC12345', 'XYZ67890' },
    },
}

Callbacks

Callbacks : Injecter la Logique de Votre Serveur

Les callbacks vous permettent d'ecrire votre propre logique dans le flux de la resource, sans modifier aucun fichier interne. Tout se fait dans config/config.lua. Utilisez-les pour decider qui peut utiliser, ce qui se passe a l'equipement, ce qui se passe au retrait, et toute regle personnalisee de votre serveur.

Tableau des Callbacks

CallbackParametresRetourMoment de l'appel
CanOpenHUDsourcetrue/falseAvant d'ouvrir le HUD radial
CanEquipWingssource, cortrue/falseAvant d'equiper les ailes
OnWingsEquippedsource, coraucunApres avoir equipe les ailes
OnWingsRemovedsourceaucunApres avoir retire les ailes
HasPermissionsource, permissiontrue/false/nilAvant toute verification de permission
A propos de CanEquipWingsLe parametre cor peut etre nil ou un number. Quand il est nil, le serveur verifie si le bouton "Prendre les Ailes" du HUD doit etre active. Quand c'est un nombre, c'est une tentative reelle d'equipement. Gerez les deux cas dans votre callback.

Scenarios avec exemples complets

Chaque scenario ci-dessous est complet et autonome. Copiez ce qui correspond a votre serveur.

Exiger un item dans l'inventaire pour equiper (et le rendre au retrait) ESX

Le joueur doit avoir l'item fairy_essence dans son inventaire. A l'equipement, l'item est consomme. Au retrait des ailes, l'item est rendu dans l'inventaire.

config.lua
Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if cor then
            -- Tentative reelle d'equipement : verifier l'item
            local xPlayer = ESX.GetPlayerFromId(source)
            local item = xPlayer.getInventoryItem('fairy_essence')
            if not item or item.count < 1 then
                Bridge.Notify(source, 'Vous avez besoin d\'Essence de Fee !', 'error')
                return false
            end
            return true
        end
        -- cor = nil : verification si le HUD affiche le bouton
        return true
    end,

    OnWingsEquipped = function(source, cor)
        -- Retirer l'item de l'inventaire apres equipement
        local xPlayer = ESX.GetPlayerFromId(source)
        xPlayer.removeInventoryItem('fairy_essence', 1)
    end,

    OnWingsRemoved = function(source)
        -- Rendre l'item au retrait
        local xPlayer = ESX.GetPlayerFromId(source)
        xPlayer.addInventoryItem('fairy_essence', 1)
    end,
}
Exiger un item dans l'inventaire pour equiper (et le rendre au retrait) QB-Core

Meme logique que pour ESX, mais en utilisant les fonctions de QB-Core.

config.lua
Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if cor then
            local Player = QBCore.Functions.GetPlayer(source)
            local item = Player.Functions.GetItemByName('fairy_essence')
            if not item then
                TriggerClientEvent('QBCore:Notify', source, 'Vous avez besoin d\'Essence de Fee !', 'error')
                return false
            end
            return true
        end
        return true
    end,

    OnWingsEquipped = function(source, cor)
        local Player = QBCore.Functions.GetPlayer(source)
        Player.Functions.RemoveItem('fairy_essence', 1)
    end,

    OnWingsRemoved = function(source)
        local Player = QBCore.Functions.GetPlayer(source)
        Player.Functions.AddItem('fairy_essence', 1)
    end,
}

Config.Callbacks = {

        local user_id = vRP.getUserId(source)
        vRP.tryGiveInventoryItem(user_id, 'essencia_fada', 1)

Le joueur doit se trouver a un endroit specifique Tous Frameworks

Le joueur ne peut equiper que s'il se trouve dans une zone definie. Utile pour creer des "temples", autels ou zones magiques ou les ailes sont autorisees.

config.lua
-- Zone autorisee (coordonnees centrales + rayon)
local ZONA_ALTAR = { x = -1042.5, y = -2745.3, z = 13.9, raio = 15.0 }

Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if cor then
            -- Recuperer la position actuelle du joueur
            local ped = GetPlayerPed(source)
            local coords = GetEntityCoords(ped)

            -- Calculer la distance jusqu'a l'autel
            local dx = coords.x - ZONA_ALTAR.x
            local dy = coords.y - ZONA_ALTAR.y
            local dz = coords.z - ZONA_ALTAR.z
            local dist = math.sqrt(dx*dx + dy*dy + dz*dz)

            if dist > ZONA_ALTAR.raio then
                Bridge.Notify(source, 'Vous devez etre a l\'Autel des Fees !', 'error')
                return false
            end
        end
        return true
    end,
}

Si votre serveur dispose d'un systeme de quetes ou de progression, vous pouvez verifier si le joueur a accompli une etape avant de debloquer les ailes. Cet exemple utilise des exports d'une resource de quetes generique, adaptez-le au systeme de votre serveur.

Config.Callbacks = {

}

Ailes reservees aux VIPs (ou tout groupe ACE) Tous Frameworks

Bloquer a la fois le HUD et l'equipement pour ceux qui ne sont pas VIP. Peut etre utilise avec tout groupe ACE de votre serveur.

config.lua
Config.Callbacks = {
    HasPermission = function(source, permission)
        if permission == 'use' then
            return IsPlayerAceAllowed(source, 'group.vip')
        end
        return nil  -- Autres permissions : utiliser le systeme par defaut
    end,

    CanOpenHUD = function(source)
        if not IsPlayerAceAllowed(source, 'group.vip') then
            Bridge.Notify(source, 'Les Ailes de Fee sont exclusives aux VIPs !', 'error')
            return false
        end
        return true
    end,
}
Combiner plusieurs regles : item + lieu + niveau ESX

Exemple complet combinant plusieurs conditions. Le joueur doit avoir un item, se trouver a un endroit specifique et avoir un niveau minimum. Montre comment composer des regles complexes dans un seul callback.

config.lua
local ALTAR = { x = -1042.5, y = -2745.3, z = 13.9, raio = 15.0 }

Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if not cor then return true end  -- Verification HUD : autoriser l'affichage

        -- Regle 1 : L'item est requis
        local xPlayer = ESX.GetPlayerFromId(source)
        local item = xPlayer.getInventoryItem('fairy_essence')
        if not item or item.count < 1 then
            Bridge.Notify(source, 'Vous avez besoin d\'Essence de Fee !', 'error')
            return false
        end

        -- Regle 2 : Doit etre a l'autel
        local ped = GetPlayerPed(source)
        local c = GetEntityCoords(ped)
        local dist = #(vector3(c.x, c.y, c.z) - vector3(ALTAR.x, ALTAR.y, ALTAR.z))
        if dist > ALTAR.raio then
            Bridge.Notify(source, 'Rendez-vous a l\'Autel des Fees !', 'error')
            return false
        end

        -- Regle 3 : Niveau minimum (export de votre systeme)
        local level = exports['meu_level_system']:getLevel(source)
        if level < 30 then
            Bridge.Notify(source, 'Vous devez etre niveau 30 !', 'error')
            return false
        end

        return true
    end,

    OnWingsEquipped = function(source, cor)
        local xPlayer = ESX.GetPlayerFromId(source)
        xPlayer.removeInventoryItem('fairy_essence', 1)
        exports['meu_level_system']:addXP(source, 50)
    end,
}
Override total de la permission avec votre propre logique Tous Frameworks

Si vous avez votre propre systeme de permissions sur le serveur et que vous voulez ignorer completement le systeme a 8 couches, utilisez le callback HasPermission. Retourner true ou false ignore toutes les verifications par defaut. Retourner nil laisse le systeme continuer normalement.

config.lua
Config.Callbacks = {
    HasPermission = function(source, permission)
        if permission == 'use' then
            -- Utiliser votre propre systeme de permissions
            return exports['meu_perm_system']:hasPermission(source, 'fairy_wings')
        end

        if permission == 'admin_cleanup' then
            return IsPlayerAceAllowed(source, 'group.admin')
        end

        return nil  -- Pour toute permission inconnue, utiliser le defaut
    end,
}
Permission basee sur les roles Discord Tous Frameworks

Supposons que vous voulez baser votre systeme de permissions sur les roles Discord. C'est possible ! Il suffit d'avoir une resource d'integration Discord sur le serveur (comme badger_discord_api, discord_perms, deek_discord, etc.) qui fournit un export pour verifier les roles. Le callback HasPermission fait le reste.

config.lua
Config.Callbacks = {
    HasPermission = function(source, permission)
        if permission == 'use' then
            -- ID du role "Fee" sur Discord (clic droit sur le role > Copier l'ID)
            local hasCargo = exports['badger_discord_api']:isRolePresent(source, 1234567890123456)
            return hasCargo  -- true = a le role, false = ne l'a pas
        end

        if permission == 'admin_cleanup' then
            -- ID du role "Admin" sur Discord
            return exports['badger_discord_api']:isRolePresent(source, 9876543210987654)
        end

        return nil  -- autres permissions : utiliser le systeme par defaut
    end,
}
Combiner Discord + systeme par defautSi vous voulez que le joueur ait acces s'il a le role Discord OU s'il passe le systeme par defaut (vRP, ACE, job, etc.), retournez simplement nil quand le role n'est pas trouve. Ainsi le systeme continue a verifier les 7 autres couches normalement :
config.lua
Config.Callbacks = {
    HasPermission = function(source, permission)
        if permission == 'use' then
            local discordOk = exports['badger_discord_api']:isRolePresent(source, 1234567890123456)
            if discordOk then return true end
            return nil  -- pas de role Discord ? laisser le systeme par defaut verifier vRP/ACE/etc
        end
        return nil
    end,
}
Evenements et Integration

Evenements : Ecouter et Integrer

La resource declenche divers evenements tout au long du cycle de vie des ailes. Vous pouvez ecouter ces evenements depuis d'autres resources pour creer des integrations, synchroniser des systemes ou reagir lorsque quelque chose se produit.

Nomenclature des evenements

Tous les evenements sont prefixes automatiquement avec le nom de la resource pour eviter les conflits. Le prefixe suit le schema :

lua
-- Format : NomDeLaResource:type:action
-- Exemple :
'MathStoreFairyWing-V7:spawn'          -- Commande (server → client)
'MathStoreFairyWing-V7:sync:spawned'   -- Synchronisation (client → server)
'MathStoreFairyWing-V7:sync:spawn'     -- Broadcast (server → autres clients)
A propos des nomsLes noms exacts sont generes automatiquement dans bridge/shared.lua en utilisant GetCurrentResourceName(). Ci-dessous, nous utilisons le nom par defaut MathStoreFairyWing-V7.

Evenements Client → Server (Synchronisation)

Quand le joueur fait quelque chose localement, le client envoie ces evenements au serveur pour que les autres joueurs voient :

Scenarios d'integration avec exemples complets

Chaque scenario ci-dessous montre comment ecouter ou reagir aux evenements de la resource a partir d'une autre resource de votre serveur.

Reagir quand un joueur commence ou arrete de voler Client - Autre Resource

Votre resource de HUD ou systeme de statuts peut ecouter le debut/fin du vol pour afficher un indicateur, appliquer un effet ou modifier la camera.

client.lua (autre resource)
-- Le joueur a commence a voler
AddEventHandler('flight:start', function(playerId)
    print('[MonHUD] Joueur en vol : ' .. playerId)
    -- Activer l'indicateur de vol dans le HUD
    SendNUIMessage({ action = 'showFlightIndicator', active = true })
end)

-- Le joueur a arrete de voler
AddEventHandler('flight:end', function(playerId)
    print('[MonHUD] Joueur a atterri : ' .. playerId)
    SendNUIMessage({ action = 'showFlightIndicator', active = false })
end)

-- L'animation de vol a change (ex: planer, battre des ailes, descendre)
AddEventHandler('flight:animationChange', function(playerId, state)
    print('[MonHUD] Animation vol : ' .. state)
end)
Detecter un mode de vol specifique (rase-mottes, montee) Client - Autre Resource

Si vous souhaitez appliquer des effets visuels differents selon le type de manoeuvre que le joueur effectue en vol.

client.lua (autre resource)
-- Mode rase-mottes (vol bas rapide)
AddEventHandler('wing:rasanteActive', function(active)
    if active then
        -- Appliquer un effet de vitesse, motion blur, etc.
        SetTimecycleModifier('spectator5')
    else
        ClearTimecycleModifier()
    end
end)

-- Mode montee (gain d'altitude)
AddEventHandler('wing:subidaActive', function(active)
    if active then
        -- Particules de vent, trainee, etc.
    end
end)
Ecouter cote serveur quand quelqu'un equipe/retire des ailes Server - Autre Resource

Depuis une autre resource sur le serveur, vous pouvez ecouter les evenements de sync pour logger, donner une recompense, notifier Discord, etc.

server.lua (autre resource)
-- Ecouter quand quelqu'un a equipe des ailes
RegisterNetEvent('MathStoreFairyWing-V7:sync:spawned')
AddEventHandler('MathStoreFairyWing-V7:sync:spawned', function(cor, initialState)
    local src = source
    print('[Log] Joueur ' .. src .. ' a equipe des ailes couleur ' .. cor)

    -- Exemple : envoyer vers Discord
    exports['discord_log']:sendLog('wings', 
        GetPlayerName(src) .. ' a equipe des ailes (couleur ' .. cor .. ')'
    )
end)

-- Ecouter quand quelqu'un a retire ses ailes
RegisterNetEvent('MathStoreFairyWing-V7:sync:removed')
AddEventHandler('MathStoreFairyWing-V7:sync:removed', function()
    local src = source
    print('[Log] Joueur ' .. src .. ' a retire ses ailes')
end)
A propos de l'ecoute des net eventsQuand vous enregistrez un RegisterNetEvent depuis une autre resource, vous ecoutez le meme evenement que le Fairy Wing V7 ecoute deja en interne. FiveM autorise les handlers multiples. Votre logique s'execute en parallele, sans interferer avec la resource d'origine.
Reagir aux changements d'animation d'un autre joueur Client - Autre Resource

Quand un autre joueur change d'animation (ex: ouvre les ailes), le broadcast arrive sur votre client. Vous pouvez l'utiliser pour creer des effets visuels synchronises.

client.lua (autre resource)
RegisterNetEvent('MathStoreFairyWing-V7:sync:anim')
AddEventHandler('MathStoreFairyWing-V7:sync:anim', function(serverId, animKey)
    print('[Sync] Joueur ' .. serverId .. ' a change d\'animation pour : ' .. animKey)

    -- Exemple : Creer des particules autour quand quelqu'un ouvre les ailes
    if animKey == 'open' or animKey == 'bater' then
        local ped = GetPlayerPed(GetPlayerFromServerId(serverId))
        if ped and ped ~= 0 then
            -- Ajouter une particule sur le ped
        end
    end
end)

Declencher des evenements du Fairy Wing V7 depuis une autre resource

Les scenarios ci-dessus montrent comment ecouter les evenements. Mais vous pouvez aussi declencher des evenements du Fairy Wing V7 directement depuis votre resource, sans dependre des commandes. C'est utile quand le flux demarre en dehors du Fairy Wing V7 (boutique, item, PNJ, quete, etc.).

ImportantQuand vous declenchez l'evenement directement, vous contournez le systeme de permissions et de callbacks du Fairy Wing V7. La responsabilite de verifier si le joueur peut ou non utiliser revient a VOTRE resource. Utilisez cela uniquement quand vous voulez un controle total du flux.
Boutique ou PNJ qui donne des ailes au joueur a l'achat Server - Autre Resource

Le joueur interagit avec un PNJ ou une boutique, paie et recoit les ailes directement. Depuis le serveur de votre resource, vous envoyez l'evenement :spawn au client du joueur.

server.lua (autre resource - ex: boutique)
-- Le joueur a achete des ailes dans la boutique, couleur 5
RegisterNetEvent('minhaLoja:comprarAsas')
AddEventHandler('minhaLoja:comprarAsas', function(cor)
    local src = source

    -- Votre logique de paiement
    local xPlayer = ESX.GetPlayerFromId(src)
    if xPlayer.getMoney() < 5000 then
        TriggerClientEvent('esx:showNotification', src, 'Fonds insuffisants !')
        return
    end
    xPlayer.removeMoney(5000)

    -- Donner les ailes au joueur (declenche directement le Fairy Wing V7)
    TriggerClientEvent('MathStoreFairyWing-V7:spawn', src, cor)
end)
Item utilisable qui equipe les ailes a l'utilisation ESX

Vous enregistrez un item utilisable sur le serveur. Quand le joueur utilise l'item, les ailes sont equipees automatiquement et l'item est consomme.

server.lua (autre resource - ex: items)
-- Enregistrer l'item utilisable 'asas_de_fada'
ESX.RegisterUsableItem('asas_de_fada', function(source)
    local src = source
    local xPlayer = ESX.GetPlayerFromId(src)

    -- Consommer l'item
    xPlayer.removeInventoryItem('asas_de_fada', 1)

    -- Equiper les ailes couleur 1
    TriggerClientEvent('MathStoreFairyWing-V7:spawn', src, 1)
end)

Flux complet : de la commande a la synchronisation

Pour comprendre comment tout se connecte, voici le flux complet lorsqu'un joueur tape /asas7 5 :

Joueur : /asas7 5 ↓ Server : Recoit la commande enregistree ↓ Bridge.HasPermission(source, 'use') → Verification des 8 couches (voir section Permissions) ↓ SANS permission ? → Bridge.Notify() + STOP ↓ Bridge.ExecuteCallback('CanEquipWings', source, 5) → Execute le callback de votre config.lua ↓ Le callback a retourne false ? → STOP ↓ TriggerClientEvent(':spawn', source, 5) ↓ Client : Cree l'entite de l'aile, applique la couleur 5 ↓ TriggerServerEvent(':sync:spawned', 5, 'idle') ↓ Server : Sauvegarde dans activeWings[source] Bridge.ExecuteCallback('OnWingsEquipped', source, 5) ↓ broadcastBucket(':sync:spawn', bucket, source, src, 5, 'idle') ↓ Les autres joueurs dans le meme bucket voient les ailes apparaitre

Routing Buckets, StateBag et Etat Interne

Informations avancees sur la facon dont la resource gere la synchronisation, les conflits multi-resource et l'etat interne.

Routing Buckets

La resource respecte les routing buckets de FiveM. Les joueurs dans des buckets differents ne voient pas les ailes des autres. Toute la synchronisation est filtree par bucket.

server (interne)
-- Chaque joueur avec des ailes a son bucket suivi
activeWings[serverId] = {
    cor    = 5,
    state  = 'idle',
    bucket = 0,
}

-- Les broadcasts n'envoient qu'aux joueurs dans le meme bucket
broadcastBucket(eventName, bucket, excludeSource, ...)

-- Quand le bucket change (verifie toutes les 2s) :
-- Le joueur change du bucket 0 → bucket 5
--   Joueurs dans le bucket 0 : recoivent :sync:remove
--   Joueurs dans le bucket 5 : recoivent :sync:spawn + etat
En pratiqueSi vous utilisez des appartements, instances ou tout systeme base sur les routing buckets (ex: qb-apartments, esx_property), les ailes fonctionnent correctement dans chaque instance sans interferer avec les autres.

StateBag (Multi-Resource)

Si le serveur possede plusieurs resources d'ailes MathStore (ex: DragonWings + DemonWings), le systeme utilise le StateBag pour eviter les conflits. Un seul resource peut avoir des ailes actives par joueur.

lua
-- Cle utilisee dans le state bag
WING_STATE_KEY = 'activeWingResource'

-- A l'equipement des ailes, le serveur definit :
Player(src).state:set(WING_STATE_KEY, RES_NAME, true)

-- Si une autre resource d'ailes tente d'equiper sur le meme joueur :
-- Verifie s'il existe deja une resource active
-- Si oui, peut auto-retirer la precedente

-- Le client ecoute les changements via :
AddStateBagChangeHandler(WING_STATE_KEY, ...)

Etat interne du Server

Le serveur maintient des tables d'etat qui suivent tout ce qui est actif. Utile pour comprendre le debug et le comportement :

server (interne)
-- 1. Ailes actives (indexees par server ID)
activeWings[serverId] = {
    cor    = 5,
    state  = 'idle',
    bucket = 0,
}

-- Tout est nettoye automatiquement quand le joueur se deconnecte
