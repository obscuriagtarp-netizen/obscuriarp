Setup Completo

Instalacion y Licencia

Todo lo que necesitas para poner el resource en funcionamiento. La licencia (key) es parte de la instalacion, asi que esta todo junto aqui.

1. Extraer el resource

Coloca la carpeta MathStoreFairyWing-V7 dentro de tu carpeta resources/.

Nombre de la carpetaEl nombre de la carpeta debe ser exactamente MathStoreFairyWing-V7. Keybinds, eventos internos y state bags dependen de este nombre.

2. Configurar la Key (Convar)

Cada servidor necesita una key unica para que el resource funcione. Esta key se configura como una convar en tu server.cfg, y debe ir antes del ensure.

server.cfg
## ─── MathStore Fairy Wing V7 ───

# 1. Define la key (ANTES del ensure)
set mathstore_key_fairyv7 "AP-XXXX-XXXX-XXXX"

# 2. Inicia el resource
ensure MathStoreFairyWing-V7
Cuidado con la keyNo compartas tu key. Cada key esta vinculada a la IP del servidor. Si cambias de host, contactanos para migrarla.

3. Dependencias

ResourceEstadoFuncion
ox_libOpcionalComandos con sugerencias, notificaciones estilizadas. Se activa en Config.UseOxLib
qb-core / qbx_coreAuto-detectadoBridge QB/QBX para permisos y player data
es_extendedAuto-detectadoBridge ESX para permisos y player data
vrpAuto-detectadoBridge vRP para grupos, permisos e identidad
Modo StandaloneSi ningun framework es detectado, el resource funciona por si solo. Todo funciona, solo sin integracion de permisos nativos del framework.
Configuracion

Config.lua

El archivo config/config.lua centraliza todas las opciones del resource. Todo lo que puedes cambiar esta aqui.

Framework y General

config.lua
-- Deteccion automatica del framework
Config.Framework = 'auto'     -- 'auto' | 'qbx' | 'qb' | 'esx' | 'vrp' | 'standalone'

-- Usar ox_lib para comandos y notificaciones
Config.UseOxLib = true

-- Idioma del sistema (notificaciones, keybinds, HUD)
Config.Locale = 'pt-BR'      -- 'pt-BR' | 'en-US' | 'es' | 'fr' | 'pt-PT' | 'th'
ConsejoCon Config.Framework = 'auto', el resource detecta solo cual framework esta corriendo. Solo fuerzalo manualmente si hay algun conflicto.

Notificaciones

config.lua
Config.Notifications = {
    type     = 'auto',    -- 'auto' | 'ox_lib' | 'qb' | 'esx' | 'vrp' | 'native'
    duration = 5000,     -- Duracion en milisegundos
}
ValorComportamiento
'auto'Detecta: ox_lib > framework > native (en ese orden)
'ox_lib'Fuerza ox_lib:notify
'qb'Fuerza QBCore notification
'esx'Fuerza ESX.ShowNotification
'vrp'Fuerza vRP notification
'native'Notificacion nativa de GTA V

Keybinds

config.lua
Config.Keybinds = {
    toggle = '',      -- Abrir/cerrar alas (vacio = sin tecla por defecto)
    fly    = false,    -- false = keybind desactivado
    hud    = '',      -- HUD radial (vacio = el jugador configura)
}
Como funcionaCuando el valor es '' (vacio), ninguna tecla se asigna por defecto. El jugador va a Configuracion > Teclado > FiveM y elige la tecla que quiera. El texto que aparece alli cambia segun el Config.Locale.

Multi-Framework

Sistema Bridge

El resource detecta automaticamente el framework del servidor y adapta todas las funciones internas. No necesitas configurar nada en la mayoria de los casos.

Como funciona la deteccion

En bridge/shared.lua, el sistema verifica cuales resources estan corriendo y elige el bridge correcto:

FrameworkResource DetectadoResultado
QBX (Qbox)qbx_core'qbx'
QB-Coreqb-core'qb'
ESXes_extended'esx'
vRPvrp'vrp'
Ninguno-'standalone'

Funciones del Bridge (Server-side)

Funciones disponibles en el server para interactuar con los datos del jugador:

server
-- Obtener el objeto del jugador en el framework
local player = Bridge.GetPlayer(source)

-- Obtener identificador unico (citizenid, identifier, user_id)
local cid = Bridge.GetCitizenId(source)

-- Nombre del personaje en el framework
local name = Bridge.GetPlayerName(source)

-- Job actual (nombre + grado)
local job = Bridge.GetJob(source)

-- Verificar permiso (sistema multi-capa)
local allowed = Bridge.HasPermission(source, 'use')

-- Enviar notificacion (se adapta al framework detectado)
Bridge.Notify(source, 'Mensaje', 'success')

-- Ejecutar callback definido en el config
Bridge.ExecuteCallback('CanEquipWings', source, cor)

Funciones disponibles en el client:

-- Datos del jugador en el framework

-- ¿El jugador ya termino de cargar?

Control de Acceso

Sistema de Permisos

Controla quien puede usar cada funcionalidad del resource. El sistema posee 8 capas de verificacion, evaluadas en orden. Cuando cualquier capa da una respuesta definitiva (permitir o denegar), las siguientes no se verifican.

Claves de Permiso

Existen dos claves usadas en todo el sistema:

ClaveDonde se usaDescripcion
'use'Todos los comandos de alas, HUD, animacionesPermiso general para usar el resource
'admin_cleanup'/asaslimpar7Permiso admin para limpiar todas las alas del servidor

Flujo completo de verificacion (8 capas)

Cuando un jugador ejecuta cualquier comando, el permiso se verifica en este orden:

1. Config.Callbacks.HasPermission(source, permission) → ¿Retorna true/false? Lo usa y se detiene aqui → ¿Retorna nil? Continua a la siguiente capa 2. ACE Permission: IsPlayerAceAllowed(source, Permissions.Ace[perm]) → Ej: 'MathStoreFairyWing-V7.use' (generado automaticamente) 3. Feature Config: Permissions.Features[perm].enabled → Si enabled = false, TODOS tienen acceso (sin restriccion) 4. CitizenID: Permissions.Features[perm].citizenids → Lista de IDs especificos permitidos 5. vRP Groups: Permissions.VRP[perm] → Ej: {'Fada', 'Admin'} 6. Sets (QBX): Permissions.Features[perm].sets 7. ACE Groups: Permissions.Groups[grupo] → Verifica group.admin, group.vip, etc. 8. Jobs: Permissions.Features[perm].jobs → Ej: {'police', 'ambulance'}

Permitir para todos (sin ninguna restriccion)

permissions.lua
Permissions.Features = {
    use = {
        enabled = false,    -- false = TODOS pueden usar, sin verificacion
    },
}

Restringir por grupo vRP

permissions.lua
Permissions.VRP = {
    use = { 'Fada', 'Admin' },            -- Nombres exactos de los grupos vRP
    admin_cleanup = { 'Admin' },
}

Restringir por ACE Permission

El resource genera los nombres ACE automaticamente usando GetCurrentResourceName(). Es decir, si la carpeta es MathStoreFairyWing-V7, los ACEs quedan:

permissions.lua
Permissions.Ace = {
    use = GetCurrentResourceName() .. '.use',             -- 'MathStoreFairyWing-V7.use'
    admin_cleanup = GetCurrentResourceName() .. '.admin',  -- 'MathStoreFairyWing-V7.admin'
}
server.cfg
# Liberar uso para grupo VIP
add_ace group.vip MathStoreFairyWing-V7.use allow

# Liberar admin cleanup
add_ace group.admin MathStoreFairyWing-V7.admin allow

Restringir por Job (QB/ESX)

permissions.lua
Permissions.Features = {
    use = {
        enabled = true,
        jobs = { 'police', 'ambulance' },   -- Nombre del job en el framework
    },
}

Restringir por CitizenID especifico

permissions.lua
Permissions.Features = {
    use = {
        enabled = true,
        citizenids = { 'ABC12345', 'XYZ67890' },
    },
}

Callbacks

Callbacks: Inyectando Logica de Tu Servidor

Los callbacks permiten que escribas tu propia logica dentro del flujo del resource, sin editar ningun archivo interno. Todo queda en config/config.lua. Usalos para decidir quien puede usar, que sucede al equipar, que sucede al remover, y cualquier regla personalizada de tu servidor.

Tabla de Callbacks

CallbackParametrosRetornoMomento de la llamada
CanOpenHUDsourcetrue/falseAntes de abrir la HUD radial
CanEquipWingssource, cortrue/falseAntes de equipar alas
OnWingsEquippedsource, corningunoDespues de equipar alas
OnWingsRemovedsourceningunoDespues de remover alas
HasPermissionsource, permissiontrue/false/nilAntes de cualquier verificacion de permiso
Sobre el CanEquipWingsEl parametro cor puede ser nil o un number. Cuando es nil, el server esta verificando si el boton "Obtener Ala" de la HUD debe estar habilitado. Cuando es un numero, es un intento real de equipar. Maneja ambos casos en tu callback.

Escenarios con ejemplos completos

Cada escenario a continuacion es completo y auto-contenido. Copia lo que tenga sentido para tu servidor.

Requerir item en el inventario para equipar (y devolver al remover) ESX

El jugador necesita tener el item fairy_essence en el inventario. Al equipar, el item se consume. Al remover las alas, el item vuelve al inventario.

config.lua
Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if cor then
            -- Intento real de equipar: verificar item
            local xPlayer = ESX.GetPlayerFromId(source)
            local item = xPlayer.getInventoryItem('fairy_essence')
            if not item or item.count < 1 then
                Bridge.Notify(source, '¡Necesitas Esencia de Hada!', 'error')
                return false
            end
            return true
        end
        -- cor = nil: solo verificando si la HUD muestra el boton
        return true
    end,

    OnWingsEquipped = function(source, cor)
        -- Remover item del inventario despues de equipar
        local xPlayer = ESX.GetPlayerFromId(source)
        xPlayer.removeInventoryItem('fairy_essence', 1)
    end,

    OnWingsRemoved = function(source)
        -- Devolver item al remover
        local xPlayer = ESX.GetPlayerFromId(source)
        xPlayer.addInventoryItem('fairy_essence', 1)
    end,
}

El jugador necesita estar en un lugar especifico Cualquier Framework

El jugador solo puede equipar si esta dentro de un area definida. Util para crear "templos", altares o zonas magicas donde las alas se liberan.

config.lua
-- Area permitida (coordenadas centrales + radio)
local ZONA_ALTAR = { x = -1042.5, y = -2745.3, z = 13.9, raio = 15.0 }

Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if cor then
            -- Obtener la posicion actual del jugador
            local ped = GetPlayerPed(source)
            local coords = GetEntityCoords(ped)

            -- Calcular distancia hasta el altar
            local dx = coords.x - ZONA_ALTAR.x
            local dy = coords.y - ZONA_ALTAR.y
            local dz = coords.z - ZONA_ALTAR.z
            local dist = math.sqrt(dx*dx + dy*dy + dz*dz)

            if dist > ZONA_ALTAR.raio then
                Bridge.Notify(source, '¡Necesitas estar en el Altar de las Hadas!', 'error')
                return false
            end
        end
        return true
    end,
}

Si tu servidor tiene sistema de quests o progresion, puedes verificar si el jugador completo una etapa antes de liberar las alas. Este ejemplo usa exports de un resource de quests generico, adaptalo al sistema de tu servidor.

Config.Callbacks = {

Alas solo para VIPs (o cualquier ACE group) Cualquier Framework

Bloquear tanto la HUD como el equipar para quien no sea VIP. Se puede usar con cualquier grupo ACE de tu servidor.

Combinar varias reglas: item + lugar + nivel ESX

Ejemplo completo combinando varias condiciones. El jugador necesita tener un item, estar en un lugar especifico y tener nivel minimo. Muestra como componer reglas complejas en un unico callback.

config.lua
local ALTAR = { x = -1042.5, y = -2745.3, z = 13.9, raio = 15.0 }

Config.Callbacks = {
    CanEquipWings = function(source, cor)
        if not cor then return true end  -- HUD check: permitir visual

        -- Regla 1: Necesita el item
        local xPlayer = ESX.GetPlayerFromId(source)
        local item = xPlayer.getInventoryItem('fairy_essence')
        if not item or item.count < 1 then
            Bridge.Notify(source, '¡Necesitas Esencia de Hada!', 'error')
            return false
        end

        -- Regla 2: Necesita estar en el altar
        local ped = GetPlayerPed(source)
        local c = GetEntityCoords(ped)
        local dist = #(vector3(c.x, c.y, c.z) - vector3(ALTAR.x, ALTAR.y, ALTAR.z))
        if dist > ALTAR.raio then
            Bridge.Notify(source, '¡Ve al Altar de las Hadas!', 'error')
            return false
        end

        -- Regla 3: Nivel minimo (export de tu sistema)
        local level = exports['meu_level_system']:getLevel(source)
        if level < 30 then
            Bridge.Notify(source, '¡Necesitas ser nivel 30!', 'error')
            return false
        end

        return true
    end,

    OnWingsEquipped = function(source, cor)
        local xPlayer = ESX.GetPlayerFromId(source)
        xPlayer.removeInventoryItem('fairy_essence', 1)
        exports['meu_level_system']:addXP(source, 50)
    end,
}
Override total del permiso con logica propia Cualquier Framework

Si tienes un sistema de permisos propio en el servidor y quieres ignorar completamente el sistema de 8 capas, usa el callback HasPermission. Retornar true o false salta todas las verificaciones por defecto. Retornar nil deja que el sistema continue normalmente.

config.lua
Config.Callbacks = {
    HasPermission = function(source, permission)
        if permission == 'use' then
            -- Usar tu propio sistema de permisos
            return exports['meu_perm_system']:hasPermission(source, 'fairy_wings')
        end

        if permission == 'admin_cleanup' then
            return IsPlayerAceAllowed(source, 'group.admin')
        end

        return nil  -- Para cualquier permiso desconocido, usar por defecto
    end,
}
Permiso basado en roles de Discord Cualquier Framework

Supongamos que quieres basar tu sistema de permisos en roles de Discord. ¡Es posible! Solo necesitas un resource de integracion Discord en el servidor (como badger_discord_api, discord_perms, deek_discord, etc.) que proporcione un export para verificar roles. El callback HasPermission hace el resto.

config.lua
Config.Callbacks = {
    HasPermission = function(source, permission)
        if permission == 'use' then
            -- ID del rol "Hada" en Discord (clic derecho en el rol > Copiar ID)
            local hasCargo = exports['badger_discord_api']:isRolePresent(source, 1234567890123456)
            return hasCargo  -- true = tiene rol, false = no tiene
        end

        if permission == 'admin_cleanup' then
            -- ID del rol "Admin" en Discord
            return exports['badger_discord_api']:isRolePresent(source, 9876543210987654)
        end

        return nil  -- otros permisos: usar sistema por defecto
    end,
}
Combinando Discord + sistema por defectoSi quieres que el jugador tenga acceso si tiene el rol de Discord O si pasa por el sistema por defecto (vRP, ACE, job, etc.), solo retorna nil cuando el rol no se encuentre. Asi el sistema continua verificando las otras 7 capas normalmente:
config.lua
Config.Callbacks = {
    HasPermission = function(source, permission)
        if permission == 'use' then
            local discordOk = exports['badger_discord_api']:isRolePresent(source, 1234567890123456)
            if discordOk then return true end
            return nil  -- ¿no tiene rol Discord? deja que el sistema por defecto verifique vRP/ACE/etc
        end
        return nil
    end,
}
Eventos e Integracion

Eventos: Escuchando e Integrando

El resource dispara diversos eventos a lo largo del ciclo de vida de las alas. Puedes escuchar estos eventos desde otros resources para crear integraciones, sincronizar sistemas, o reaccionar cuando algo sucede.

Nomenclatura de los eventos

Todos los eventos estan prefijados automaticamente con el nombre del resource para evitar conflictos. El prefijo sigue el patron:

lua
-- Formato: NombreDelResource:tipo:accion
-- Ejemplo:
'MathStoreFairyWing-V7:spawn'          -- Comando (server → client)
'MathStoreFairyWing-V7:sync:spawned'   -- Sincronizacion (client → server)
'MathStoreFairyWing-V7:sync:spawn'     -- Broadcast (server → otros clients)
Sobre los nombresLos nombres exactos se generan automaticamente en bridge/shared.lua usando GetCurrentResourceName(). A continuacion, usamos el nombre por defecto MathStoreFairyWing-V7.

Eventos Client → Server (Sincronizacion)

Cuando el jugador hace algo localmente, el client envia estos eventos al server para que otros jugadores lo vean:

EventoParametrosCuando se envia

MathStoreFairyWing-V7:sync:removed-Alas removidas localmente
MathStoreFairyWing-V7:sync:requestBulk-Jugador solicita estado actual (al conectar)

Cuando un comando es validado en el server (permisos + callbacks), el server envia al client para ejecutar. Estos van dirigidos al jugador que ejecuto el comando:

Escenarios de integracion con ejemplos completos

Cada escenario a continuacion muestra como escuchar o reaccionar a eventos del resource desde otro resource de tu servidor.

Reaccionar cuando un jugador comienza o deja de volar Client - Otro Resource

Tu resource de HUD o sistema de status puede escuchar el inicio/fin del vuelo para mostrar un indicador, aplicar efecto, o alterar la camara.

client.lua (otro resource)
-- El jugador comenzo a volar
AddEventHandler('flight:start', function(playerId)
    print('[MiHUD] Jugador volando: ' .. playerId)
    -- Activar indicador de vuelo en la HUD
    SendNUIMessage({ action = 'showFlightIndicator', active = true })
end)

-- El jugador dejo de volar
AddEventHandler('flight:end', function(playerId)
    print('[MiHUD] Jugador aterrizo: ' .. playerId)
    SendNUIMessage({ action = 'showFlightIndicator', active = false })
end)

-- La animacion de vuelo cambio (ej: planeando, batiendo alas, descendiendo)
AddEventHandler('flight:animationChange', function(playerId, state)
    print('[MiHUD] Animacion vuelo: ' .. state)
end)

Escuchar en el server cuando alguien equipa/remueve alas Server - Otro Resource

Desde otro resource en el server, puedes escuchar los eventos de sync para loguear, dar recompensa, notificar a Discord, etc.

server.lua (otro resource)
-- Escuchar cuando alguien equipo alas
RegisterNetEvent('MathStoreFairyWing-V7:sync:spawned')
AddEventHandler('MathStoreFairyWing-V7:sync:spawned', function(cor, initialState)
    local src = source
    print('[Log] Jugador ' .. src .. ' equipo alas color ' .. cor)

    -- Ejemplo: enviar a Discord
    exports['discord_log']:sendLog('wings', 
        GetPlayerName(src) .. ' equipo alas (color ' .. cor .. ')'
    )
end)

-- Escuchar cuando alguien removio alas
RegisterNetEvent('MathStoreFairyWing-V7:sync:removed')
AddEventHandler('MathStoreFairyWing-V7:sync:removed', function()
    local src = source
    print('[Log] Jugador ' .. src .. ' removio alas')
end)
Sobre escuchar net eventsCuando registras un RegisterNetEvent desde otro resource, estas escuchando el mismo evento que el Fairy Wing V7 ya escucha internamente. FiveM permite multiples handlers. Tu logica se ejecuta junto, sin interferir en el resource original.
Reaccionar a cambios de animacion de otro jugador Client - Otro Resource

Cuando otro jugador cambia de animacion (ej: abre alas), el broadcast llega a tu client. Puedes usarlo para crear efectos visuales sincronizados.

client.lua (otro resource)
RegisterNetEvent('MathStoreFairyWing-V7:sync:anim')

        local ped = GetPlayerPed(GetPlayerFromServerId(serverId))

        end

Disparando eventos del Fairy Wing V7 desde otro resource

Los escenarios anteriores muestran como escuchar eventos. Pero tambien puedes disparar eventos del Fairy Wing V7 directamente desde tu resource, sin depender de comandos. Esto es util cuando el flujo comienza fuera del Fairy Wing V7 (tienda, item, NPC, quest, etc.).

ImportanteCuando disparas el evento directamente, saltas el sistema de permisos y callbacks del Fairy Wing V7. La responsabilidad de verificar si el jugador puede o no usar queda en TU resource. Usa esto solo cuando quieras control total del flujo.
Tienda o NPC que da alas al jugador al comprar Server - Otro Resource

El jugador interactua con un NPC o tienda, paga, y recibe las alas directamente. Desde el server de tu resource, envias el evento :spawn al client del jugador.

server.lua (otro resource - ej: tienda)
-- Jugador compro alas en la tienda, color 5
RegisterNetEvent('miTienda:comprarAlas')
AddEventHandler('miTienda:comprarAlas', function(cor)
    local src = source

    -- Tu logica de pago
    local xPlayer = ESX.GetPlayerFromId(src)
    if xPlayer.getMoney() < 5000 then
        TriggerClientEvent('esx:showNotification', src, '¡Dinero insuficiente!')
        return
    end
    xPlayer.removeMoney(5000)

    -- Dar las alas al jugador (dispara directo en Fairy Wing V7)
    TriggerClientEvent('MathStoreFairyWing-V7:spawn', src, cor)
end)
Item usable que equipa alas al usar ESX

Registras un item usable en el server. Cuando el jugador usa el item, las alas se equipan automaticamente y el item se consume.

server.lua (otro resource - ej: items)
-- Registrar item usable 'asas_de_fada'
ESX.RegisterUsableItem('asas_de_fada', function(source)
    local src = source
    local xPlayer = ESX.GetPlayerFromId(src)

    -- Consumir el item
    xPlayer.removeInventoryItem('asas_de_fada', 1)

    -- Equipar alas color 1
    TriggerClientEvent('MathStoreFairyWing-V7:spawn', src, 1)
end)

Flujo completo: del comando hasta la sincronizacion

Para entender como todo se conecta, aqui esta el flujo completo de cuando un jugador escribe /asas7 5:

Jugador: /asas7 5 ↓ Server: Recibe comando registrado ↓ Bridge.HasPermission(source, 'use') → Verificacion de 8 capas (ver seccion Permisos) ↓ ¿SIN permiso? → Bridge.Notify() + STOP ↓ Bridge.ExecuteCallback('CanEquipWings', source, 5) → Ejecuta el callback de tu config.lua ↓ ¿Callback retorno false? → STOP ↓ TriggerClientEvent(':spawn', source, 5) ↓ Client: Crea la entidad del ala, aplica color 5 ↓ TriggerServerEvent(':sync:spawned', 5, 'idle') ↓ Server: Guarda en activeWings[source] Bridge.ExecuteCallback('OnWingsEquipped', source, 5) ↓ broadcastBucket(':sync:spawn', bucket, source, src, 5, 'idle') ↓ Los demas jugadores en el mismo bucket ven las alas aparecer

Routing Buckets, StateBag y Estado Interno

Informacion avanzada sobre como el resource gestiona sincronizacion, conflictos multi-resource y estado interno.

Routing Buckets

El resource respeta routing buckets de FiveM. Jugadores en buckets diferentes no ven las alas de los demas. Toda la sincronizacion se filtra por bucket.

server (interno)
-- Cada jugador con alas tiene su bucket rastreado
activeWings[serverId] = {
    cor    = 5,
    state  = 'idle',
    bucket = 0,
}

-- Los broadcasts solo se envian a jugadores en el mismo bucket
broadcastBucket(eventName, bucket, excludeSource, ...)

-- Cuando el bucket cambia (verificado cada 2s):
-- Jugador cambia bucket 0 → bucket 5
--   Jugadores en bucket 0: reciben :sync:remove
--   Jugadores en bucket 5: reciben :sync:spawn + estado
En la practicaSi usas apartamentos, instancias, o cualquier sistema basado en routing buckets (ej: qb-apartments, esx_property), las alas funcionan correctamente en cada instancia sin interferir en las demas.

StateBag (Multi-Resource)

Si el servidor posee multiples resources de alas de MathStore (ej: DragonWings + DemonWings), el sistema usa StateBag para evitar conflictos. Solo un resource puede tener alas activas por jugador.

lua
-- Clave usada en el state bag
WING_STATE_KEY = 'activeWingResource'

-- Al equipar alas, el server define:
Player(src).state:set(WING_STATE_KEY, RES_NAME, true)

-- Si otro resource de alas intenta equipar en el mismo jugador:
-- Verifica si ya existe un resource activo
-- Si existe, puede auto-remover el anterior

-- El client escucha cambios via:
AddStateBagChangeHandler(WING_STATE_KEY, ...)

Estado interno del Server

El server mantiene tablas de estado que rastrean todo lo que esta activo. Util para entender debug y comportamiento:

server (interno)
-- 1. Alas activas (indexado por server ID)
activeWings[serverId] = {
    cor    = 5,
    state  = 'idle',
    bucket = 0,
}

-- Todo se limpia automaticamente cuando el jugador desconecta
